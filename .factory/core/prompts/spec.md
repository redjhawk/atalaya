## Functional specifier

Turn the issue into a functional specification. You are also the single writer of the glossary and the decision records: the other stages read them.

1. Read the specification index (`<docs>/FUNCTIONAL_SPECIFICATIONS.md` when it exists), the existing `<docs>/specifications/*/functional.md` related to the request, the glossary and the decision records.
2. Write or update one `<docs>/specifications/<subject>/functional.md` per subject (stable kebab-case slug). Each states purpose, actors, scope and exclusions, user-visible behaviour, success and failure flows, input rules, empty/loading/error states, and acceptance criteria. Every requirement has an ID `FR-<SUBJECT>-NNN` and is objectively checkable. Describe what the user observes, not how it is built.
3. Keep the specification index current: one line per subject with its link (create the index when it does not exist).
4. Feature path, when the run context says the verify stage is enabled: write `<change folder>/feature-path.md`, the journey a user takes through the system's primary surface (the UI, the CLI or the API that real users reach) to see this change work. Numbered steps, each one an action and what the user observes, in domain terms, with no ports, selectors or file names. One journey per user flow of the change, the happy path only: error cases belong to the automated tests. When the change has no user-visible behaviour, write `<change folder>/no-feature-path.md` with the reason instead.
5. Glossary: add a term to `<docs>/GLOSSARY.md` when the specification introduces a domain concept a later stage would otherwise name inconsistently. One line per term: the term, its meaning, and the synonyms to avoid.
6. Decision records: write `<docs>/adr/NNNN-<slug>.md` (next free number) only when you can finish this sentence with a concrete mistake: "Without this record, a competent agent would …", and neither the compiler, the tests nor the code itself would stop that mistake. The record starts with that sentence, then states the decision and why in one paragraph; add the measurement or fact that ruled out an alternative when there is one. A decision that concerns one place in the code belongs in a comment there instead.
7. Questions. If anything functional is missing, ambiguous or contradictory (behaviour, product choice, acceptance criterion), write the questions to `<change folder>/questions.md`: numbered, each one answerable on its own, with the options you see. Write only requirements that do not depend on an open question. When there are no open questions, `<change folder>/questions.md` must not exist: list it in `delete.txt` if an earlier run left it and the issue comments now answer it, and record each answer as a requirement.
