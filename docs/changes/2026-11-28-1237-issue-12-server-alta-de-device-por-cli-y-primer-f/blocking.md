# Blocking review findings (round 2)

## R2-01 [spec] `server/src/telemetry.rs:173`

FR-TELEMETRY-002 says an accepted request sets the last contact to the moment the server received it, and the glossary defines 'última vez visto' / last contact as when the device was last heard from. The handler takes `received_at = now_ms()` at line 90, before the identity check, the body read and `BEGIN IMMEDIATE`. The busy timeout lets a writer wait up to 5 s for the lock (another request, or a CLI subcommand holding the write lock). So two accepted requests from the same device can commit out of order: request A (received_at = T) waits on the lock, request B (received_at = T + 3 ms) commits first, then A runs `UPDATE devices SET last_contact = ? WHERE id = ?` and moves the last contact back to T. The device's last contact then no longer shows the latest reception, which breaks the meaning of the field the panel will rely on. TC-031 sends ten concurrent requests but checks only the count, so it cannot catch this. Suggested fix: never move it backwards, e.g. `UPDATE devices SET last_contact = MAX(COALESCE(last_contact, 0), ?) WHERE id = ?`. Note that SQLite's multi-argument MAX returns NULL if any argument is NULL, so the COALESCE is needed. Each fix keeps its own `received_at` unchanged.

Triage: Confirmed: `received_at` is taken at the start of `receive` (server/src/telemetry.rs:90), before the identity check, the body read and `BEGIN IMMEDIATE`, and `store` writes it with a plain `UPDATE devices SET last_contact = ?` (line 173). Two accepted requests from one device can commit out of order (a slow body or a lock wait under the 5 s busy timeout), which moves the last contact back to an older reception. That breaks FR-TELEMETRY-002 read with the glossary ('última vez visto': when the device was last heard from), and the fix is one line.
