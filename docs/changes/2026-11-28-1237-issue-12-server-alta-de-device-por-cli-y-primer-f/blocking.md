# Blocking review findings (round 3)

## R3-01 [spec] `server/src/telemetry.rs:176`

Requirement: FR-TELEMETRY-002 ('Una petición aceptada fija el último contacto del device en el momento en que el server la recibió'), read with the glossary ('última vez visto': cuándo se supo por última vez del device), and TS-TELEMETRY-007 as amended in round 2: '`devices.last_contact` takes it only when it is later than the stored value'. Round 2 fixed R2-01 by changing the update to `MAX(COALESCE(last_contact, 0), ?)`, but no test was added. The R2-01 triage todo asked for one: 'Add a test that proves an older reception committed after a newer one leaves the newer last contact.' The existing tests (TC-027, TC-030, TC-038) only send receptions in increasing order, and TC-031 checks only the fix count. So the never-move-backwards behaviour is unproven: going back to the round-1 `UPDATE devices SET last_contact = ? WHERE id = ?` would still pass the whole suite. Suggested fix: the files in server/tests are locked, so add an in-source test next to the existing `#[cfg(test)] mod tests` in this file. The test enrols a device directly in the pool with `last_contact` set to a far-future value (e.g. `i64::MAX - 1` or `now + 1 day`), sends one accepted fix through `device_router`, and asserts `201`, one stored fix whose `received_at` is the real reception time, and `last_contact` unchanged at the future value. A second assertion should check that a NULL `last_contact` becomes the reception time, which guards the `COALESCE`.

Triage: Confirmed: server/src/telemetry.rs:176 now uses `MAX(COALESCE(last_contact, 0), ?)`, but no test exercises a reception older than the stored last contact. TC-027/TC-030/TC-038 only send in increasing order, so reverting to `SET last_contact = ?` passes the suite. The R2-01 blocking todo required this test, and TS-TELEMETRY-007 ('only when it is later than the stored value') is unproven.
